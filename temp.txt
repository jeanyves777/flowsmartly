## Blocker-resolution rule

When you encounter a technical, architectural, or implementation blocker:

1. Collect exact evidence:

   * relevant files and lines;
   * commits and branch state;
   * failing commands and exit codes;
   * applicable ADRs and contracts;
   * competing options and consequences.

2. Call Codex through VS Code.

3. Ask Codex one precise engineering question containing the evidence, constraints, and available options.

4. Require Codex to return:

   * recommended decision;
   * repository evidence supporting it;
   * rejected alternatives and why;
   * implementation steps;
   * required tests;
   * risks or migration concerns.

5. Evaluate the response against repository evidence.

6. If sound, adopt the recommendation, record the decision, dispatch the required work, and continue.

7. If incomplete or contradictory, send Codex a focused follow-up question with the contradiction. Do not restart the entire discussion.

8. After at most three focused Codex consultations on the same issue, select the safest option consistent with:

   * existing ADRs;
   * current dependency rules;
   * security invariants;
   * backward compatibility;
   * testable behavior;
   * minimum irreversible change.

9. Document the decision as an ADR amendment or implementation note and continue.

Codex consultation is a decision tool, not permission to stop.

If the VS Code Codex channel is temporarily unavailable, use independent read-only agents to evaluate the options, take the evidence-backed consensus, and continue. The unavailable consultation channel must not freeze unrelated work.

## Genuine external blockers

Credentials, unavailable external services, production authorization, billing decisions, and destructive external actions may remain externally blocked.

Even then:

* isolate the blocked operation;
* finish every independent task;
* implement adapters and local/test substitutes where valid;
* prepare an exact runbook;
* leave the feature immediately resumable;
* continue all other lanes.

Do not stop the whole programme because one external integration is unavailable.

* Workspace packages have no runnable `bin` or `start` scripts.

* The E2E harness does not currently apply the outbox migration.

* Wave 5 integration must land before overlapping W6 implementation lanes begin.
* VS Code and CLI work may continue, but final acceptance must use the real backend.

Do not revive retired findings without new executable evidence.
