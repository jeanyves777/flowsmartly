Approved. For V5, the correct move is a **new backend architecture**, not more rules added around the current looping system.

The main problem is likely that the current backend treats tools, skills, workflows, and agents too similarly. Without a clearly defined goal, context boundary, completion condition, and execution owner, the system keeps calling capabilities without knowing whether it is progressing.

# 1. V5 backend objective

The V5 backend should operate as a business execution system that can:

1. Understand the user’s goal.
2. Load the correct business context.
3. Discover what capabilities are available.
4. Create a bounded plan.
5. Execute deterministic actions where possible.
6. Use an agent only where reasoning is genuinely required.
7. Detect progress, failure, or lack of progress.
8. Stop, retry, repair, re-plan, or request approval.
9. Record every decision and action.
10. Continue across long-running workflows without losing state.

The backend should never run an open-ended agent loop.

# 3. Core V5 capability taxonomy

This separation is essential.

## Tool

A single atomic operation.

Examples:

```text
send_email
publish_social_post
create_contact
render_pdf
retrieve_orders
generate_image
pause_ad_campaign
```

A tool should not reason or loop.

---

## Skill

A reusable, bounded sequence of tools.

Examples:

```text
create_branded_social_post
research_prospect
prepare_proposal_pdf
recover_abandoned_cart
publish_video_campaign
```

A skill has:

* Defined inputs
* Defined outputs
* Known steps
* Completion criteria
* Failure handling
* Maximum execution time

A skill should normally be deterministic.

---

## Workflow

A durable, long-running business process.

Examples:

```text
cold_outreach_campaign
customer_onboarding
course_enrollment
abandoned_cart_recovery
review_response_process
proposal_to_signed_deal
```

A workflow can wait hours or days and resume without losing state.

---

## Agent

A goal-directed reasoning component.

Examples:

* Prospect Research Agent
* Campaign Strategy Agent
* Proposal Agent
* Content Agent
* Training Agent
* Growth Analyst Agent
* Customer Support Agent

An agent should be used only when the next step cannot be completely predetermined.

---

## Trigger

Starts work.

Examples:

* User command
* New lead
* New order
* Cart abandoned
* Review received
* Scheduled time
* Campaign performance threshold
* Incoming reply
* Course completion

---

## Policy

Controls what the system is allowed to do.

Examples:

* Never spend over $100 without approval
* Never send more than 50 cold emails per day
* Require approval before publishing
* Never contact an unsubscribed customer
* Do not generate a proposal below a margin threshold

---

## Memory

Stores relevant information with explicit scope.

Types:

* Conversation memory
* Task memory
* Customer memory
* Workspace memory
* Agent memory
* Workflow state
* Long-term business knowledge

Memory must never be treated as one unrestricted global prompt.

# 5. The Flow Kernel

The master hub should be called the **Flow Kernel**.

It should not directly contain every business feature. Its role is to control execution.

## Flow Kernel responsibilities

* Normalize the user’s request into a structured goal
* Determine the relevant workspace
* Load the necessary context
* Identify required capabilities
* Build or select a plan
* Validate the plan against policies
* Start the correct workflow, skill, or agent
* Track progress
* Evaluate results
* Detect no-progress loops
* Retry recoverable failures
* Re-plan when assumptions fail
* Request approval when needed
* Stop when the goal is reached
* Record final outcomes

---

# 6. Flow Registry

The registry is the professional catalog of everything the platform can do.

It should register:

* Tools
* Skills
* Agents
* Workflows
* Triggers
* Policies
* Data sources
* Provider adapters
* Models
* Templates

Every capability should declare:

| Field             | Purpose                                 |
| ----------------- | --------------------------------------- |
| Capability ID     | Permanent machine-readable identity     |
| Type              | Tool, skill, agent, workflow or trigger |
| Domain            | Social, email, store, training, etc.    |
| Version           | Controlled capability version           |
| Description       | What it does                            |
| Supported intents | Goals it can help accomplish            |
| Inputs            | Required structured inputs              |
| Outputs           | Guaranteed output structure             |
| Preconditions     | What must already be true               |
| Permissions       | Required user or system permission      |
| Side effects      | What external data it changes           |
| Approval policy   | Whether approval is required            |
| Cost estimate     | Credits, money or provider cost         |
| Time estimate     | Expected execution duration             |
| Timeout           | Maximum allowed time                    |
| Retry policy      | When and how retry is allowed           |
| Idempotency       | How duplicate execution is prevented    |
| Compensation      | How an action can be reversed           |
| Success criteria  | How completion is proven                |
| Failure codes     | Known failure categories                |
| Health status     | Available, degraded or disabled         |
| Owner             | Responsible internal module             |
| Audit level       | Required logging detail                 |

The kernel should never call an undocumented capability.

# 7. Context architecture

The system needs a dedicated **Context Engine**.

## Context should be assembled by scope

```text
User
└── Organization
    └── Workspace
        ├── Brand
        ├── Customers
        ├── Products
        ├── Campaigns
        ├── Channels
        ├── Policies
        ├── Current page
        ├── Current conversation
        └── Current task
```

## Context packages

Each task receives a limited context package containing:

* Goal
* Workspace
* User permissions
* Current portal location
* Relevant records
* Brand rules
* Business policies
* Conversation summary
* Current workflow state
* Previous attempts
* Budget and credit limits
* Required approval level
* Success definition

This prevents agents from receiving too much irrelevant information.

# 8. Agent execution lifecycle

```text
Receive goal
   ↓
Validate goal
   ↓
Load scoped context
   ↓
Discover capabilities
   ↓
Create bounded plan
   ↓
Policy and permission check
   ↓
Execute next step
   ↓
Observe result
   ↓
Evaluate progress
   ├── Goal achieved → Complete
   ├── Approval needed → Pause
   ├── Recoverable error → Retry
   ├── Invalid assumption → Re-plan
   ├── Missing information → Ask user
   ├── No progress → Stop and diagnose
   └── Terminal failure → Escalate
```

# 9. Start, stop, retry, innovate and repair rules

## Start

An agent may start only when:

* A structured goal exists
* Success criteria exist
* Required context is available
* Permissions are known
* Budget limits are defined
* Maximum steps are defined
* Stop conditions are defined

## Stop

The system stops when:

* Goal is achieved
* User cancels
* Approval is required
* Required information is missing
* Step limit is reached
* Cost limit is reached
* Time limit is reached
* The same state repeats
* No measurable progress occurs
* A terminal error occurs
* Policy blocks the action

## Retry

Retries must happen at the correct layer.

### Tool retry

For temporary technical failures:

* Network timeout
* Provider unavailable
* Rate limit
* Temporary database conflict

### Skill retry

Only when the complete skill can safely restart.

### Workflow retry

Resume from the failed durable step, not from the beginning.

### Agent retry

The agent should not repeat the same plan. It must change an assumption, capability, or strategy.

## Innovate

Innovation should mean bounded re-planning, not unrestricted experimentation.

An agent may produce an alternative plan when:

* The selected capability fails
* The original assumption is false
* The expected result is not achieved
* A better path is discovered within policy

## Repair

A repair process should:

1. Identify the failed output.
2. Determine the responsible step.
3. Preserve successful prior work.
4. Run the smallest corrective action.
5. Revalidate the final result.

# 10. Loop prevention

Every agent run should track:

* Goal hash
* Current state
* Previous state
* Plan version
* Capability calls
* Tool inputs
* Tool outputs
* Progress score
* Repeated-action count
* Cost consumed
* Time elapsed
* Remaining steps

Terminate or escalate when:

```text
same capability + same input + same result
```

occurs repeatedly.

The evaluator should also detect:

* Rewording without progress
* Repeated research
* Repeated planning
* Tool-call cycling
* Repeated validation
* Context expansion without action
* Attempts to retry permanent failures

# 13. Human approval model

Every action should be assigned an autonomy level.

| Level               | Behavior                                 |
| ------------------- | ---------------------------------------- |
| 0 — Suggest         | AI only recommends                       |
| 1 — Draft           | AI prepares content                      |
| 2 — Approve once    | User approves each execution             |
| 3 — Rule-based auto | AI runs when policy conditions match     |
| 4 — Autonomous      | AI runs within strict limits             |
| 5 — Restricted      | Reserved for internal trusted operations |

Examples:

* Generate proposal: Level 1
* Send proposal: Level 2
* Respond to reviews: Level 2 or 3
* Publish scheduled content: Level 3
* Change ad budget: Level 2
* Update listing hours: Level 3
* Delete customer data: restricted
